# TaskFlow — контекст и техническое задание для Codex

> Источник требований для разработки практической части курсового проекта. Сначала изучи существующий репозиторий, особенно `AGENTS.md`, `composer.json`, `package.json` и структуру Laravel. При конфликте с системными инструкциями или фактическим состоянием проекта следуй инструкциям более высокого приоритета и объясни отклонение.

## 1. Цель и границы

**Тема курсовой:** «Разработка сетевого приложения для распределённой асинхронной обработки задач с использованием очереди сообщений».

**Продукт:** TaskFlow — веб-приложение на Laravel, позволяющее пользователям создавать задания, передавать их через RabbitMQ независимым PHP Workers, видеть реальные статусы, прогресс, результаты и путь обработки на интерактивной схеме.

Нужна **завершённая практическая реализация**, а не презентационный макет. Не писать пояснительную записку, курсовую теорию и UML для отчёта. Не заменять реальные сообщения и обработчики фиктивными frontend-данными.

**Репозиторий:** `https://github.com/Chipinchik/async-task-runner`. В текущей директории уже создан Laravel 13; **не создавать второй Laravel-проект**. Работать в текущей ветке; не выполнять `git commit`, `git push`, merge, force push. Владелец проекта проверит изменения самостоятельно.

## 2. Технологический стек

- **PHP 8.3+ / Laravel 13**; Laravel Jobs и отдельные Queue Workers.
- **RabbitMQ** с Management Plugin; совместимый драйвер `vladimir-yuldashev/laravel-queue-rabbitmq`.
- **PostgreSQL** для состояния заданий, истории, пользователей и результатов.
- **Blade + Tailwind CSS + Alpine.js**, Vite; SVG/CSS/JS для визуализации.
- **Docker Compose** для воспроизводимого запуска, включая сборку frontend в контейнере.
- **HTTP polling 1–2 секунды** для мониторинга; WebSockets в текущую реализацию не добавлять.
- Не подключать без причины React, Vue, Redis, Horizon или микросервисный фреймворк.

## 3. Функции

### Пользователи и доступ

- Регистрация, вход, выход, базовый профиль.
- Роли: **user** (свои задачи) и **admin** (все задачи, статистика, мониторинг, повторы ошибок).
- Правила доступа на сервере через policies/middleware; проверка авторизации у JSON endpoints.
- Безопасный локальный способ создать admin (Artisan-команда или seeder). Не хранить реальные учётные данные в Git.

### Типы задач

1. **DemoDelayTask:** задержка 3–30 с, реальный прогресс примерно каждую секунду, результат с фактической длительностью. Требуется для демонстрации параллельности.
2. **TextAnalysisTask:** анализ Unicode-текста (RU/EN): число символов, слов, строк, уникальных слов, топ-10 по частоте; разумный лимит размера, валидация.
3. **CsvAnalysisTask:** загружаемый UTF-8 CSV до 5 МБ с заголовком: количество строк и столбцов, названия столбцов, пустые значения, min/max/sum/avg по числовым колонкам. Чтение по строкам, валидация, безопасное хранение файла, общий storage volume для app и workers.

### Интерфейс (русский язык)

- **Dashboard:** общее количество задач и счетчики по статусам, последние задания.
- **Создание задачи:** тип, соответствующая форма, валидация, подтверждение постановки.
- **Мои задачи:** список, фильтры по типу/статусу, пагинация, даты, Worker.
- **Карточка задачи:** входные параметры, результат, статус, прогресс, времена, ошибки, история событий.
- **Мониторинг:** Laravel → RabbitMQ → Workers → PostgreSQL, журнал событий и фактические показатели.
- **Админ-панель:** все задачи, ошибки и ручной повтор неудачной задачи; кнопка «Создать 6 тестовых задач» (6 реальных DemoDelayTask по 10 с) с переходом в мониторинг.
- Доступный адаптивный интерфейс без избыточной сложности.

## 4. Сетевая архитектура и надёжность

HTTP-запрос лишь валидирует и сохраняет задачу, публикует Laravel Job и быстро отвечает пользователю. **Тяжёлая работа происходит только в отдельном Worker.** RabbitMQ доставляет сообщения свободным потребителям; приложение не назначает задания им заранее.

- Состояния задачи: `queued`, `processing`, `completed`, `failed`; сохранять попытки, `progress`, `worker_id`, время постановки/старта/завершения, длительность и ошибки.
- Хранить вход/выход в PostgreSQL, а в сообщении передавать идентификатор задачи; проверить совместимость с механизмом сериализации Laravel Job.
- Записывать **реальные** события: `task_created`, `task_queued`, `task_started`, `task_progress`, `task_completed`, `task_failed`, `task_retried` (только если фактически произошли).
- Реализовать повторные попытки с лимитом и задержкой, обработку окончательных ошибок и безопасный ручной повтор.
- Обеспечить идемпотентность / защиту от повторной доставки. Не заявлять гарантию exactly-once.
- Не держать транзакцию БД открытой на всё время выполнения задачи.
- Учесть гонку между записью в БД и публикацией в брокер (`afterCommit` либо обоснованный более надёжный подход). При сбое публикации не создавать ложного впечатления, что сообщение точно находится в RabbitMQ; предусмотреть восстановление/понятную ошибку.
- Взаимодействие с брокером, журналом и БД должно быть достаточно наблюдаемым для отладки.

## 5. Мониторинг и визуализация — важнейшая часть

- Показывать: поступление задачи, очередь, какой Worker **фактически получил** сообщение, прогресс/этап выполнения, успешное завершение или ошибку, запись результата.
- Отдельные карточки активных Workers и задач, анимированные переходы состояний на SVG-схеме, журнал событий с датой и Worker ID.
- `worker_id` уникален для экземпляра; heartbeat с временем последней активности и TTL. Старый heartbeat нельзя считать доказательством, что Worker сейчас жив.
- Подключать RabbitMQ Management API **на серверной стороне** для `messages_ready`, `messages_unacknowledged` и `consumers`, если доступны. Не передавать секреты API браузеру.
- Чётко различать **статусы задач в PostgreSQL** и **фактические метрики RabbitMQ**. Если метрики недоступны — показывать «нет данных», а не придуманные значения.
- HTTP polling 1–2 секунды; не создавать лишнюю нагрузку и не перезагружать всю страницу.
- Для DemoDelay — настоящий `progress`; для коротких текстовых и CSV задач не выдумывать процент, если он не измеряется; показывать этапы или статус.
- Визуализация не должна изображать «предсказанного» Worker до момента, когда тот реально забрал сообщение.

## 6. Минимальная модель данных

Допускается корректировка с объяснением.

- `users`: стандартная модель Laravel + `role`.
- `tasks`: UUID, `user_id`, `type`, `status`, `input_data` JSON, `result_data` JSON, `progress`, `worker_id`, `attempts`, `max_attempts`, `error_message`, `queued_at`, `started_at`, `finished_at`, `duration_ms`, timestamps.
- `task_events`: ID, `task_id`, `event_type`, `worker_id`, `message`, `metadata` JSON, `created_at`.
- `worker_heartbeats`: `worker_id`, `hostname`/`instance_id`, `current_task_id`, `last_seen_at`, служебные поля.

Внешние ключи, индексы, миграции, Eloquent-модели, Form Requests и подходящие сервисы обязательны. Не складывать всю бизнес-логику в контроллеры.

## 7. Docker и локальный запуск

Минимальные сервисы: `app`, масштабируемый `worker`, `postgres`, `rabbitmq` (допустим отдельный web server или node build-stage). Избегать фиксированного `container_name` у worker. Настроить healthchecks, volumes, миграции и предсказуемую последовательность старта. Данные БД и брокера должны переживать перезапуск. Удобный запуск на Windows с Docker Desktop.

Основной тест масштабирования: `docker compose up -d --scale worker=3` (при необходимости использовать `--build` / указать уточнённую команду).

**Ожидаемая демонстрация:** 6 задач по 10 с, 3 независимых Workers; задачи должны идти примерно двумя параллельными волнами. Фактическое время может отличаться из-за накладных расходов. При одном Worker обработка последовательная.

## 8. Проверки и критерии готовности

- Автотесты: регистрация/доступ, валидация, создание задач, каждый тип обработки, переходы статусов и события, повторные попытки, идемпотентность, JSON endpoints.
- Отдельная **реальная интеграционная проверка** с RabbitMQ и PostgreSQL (моки/`Queue::fake` не подтверждают работу RabbitMQ).
- Проверить запуск контейнеров, миграции, сборку интерфейса, реальные сообщения, выполнение нескольких Workers, мониторинг и демонстрационный сценарий, если инструменты доступны.
- Исправлять найденные ошибки в ходе выполнения. Никогда не утверждать, что непроверенный компонент точно работает.

## 9. Безопасность и публичность

Публичный GitHub-репозиторий: не коммитить `.env`, пароли, токены, ключи, данные пользователя, `vendor`, `node_modules`, SQLite и артефакты. Дополнить `.gitignore` при необходимости. Сохранить `.env.example`, `composer.lock` и frontend lock-файл. Демонстрационные креды допустимы только в явном локальном профиле и должны быть безопасно задокументированы.

## 10. Что предоставить после реализации

1. Рабочий код в **текущем проекте**, без коммитов и push.
2. README **на русском**: архитектура, сервисы, переменные, сборка, запуск, миграции, создание admin, масштабирование workers, демонстрация, логи, тесты и ограничения.
3. Короткий итог: основные изменённые файлы, команды, что реально проверено и с какими результатами, известные проблемы, что осталось.

**Режим работы:** самостоятельно доводи работу до максимально полной реализации, не останавливаясь на каждом промежуточном этапе. При техническом препятствии не скрывай его; продолжай всё остальное, что можно достоверно сделать. Главный приоритет: работающая цепочка **Laravel → RabbitMQ → Worker → PostgreSQL → честная визуализация**.
